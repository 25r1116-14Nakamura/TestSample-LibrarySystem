# テスト項目選定の考え方と理由書

本ドキュメントは、作成したテストチェックリスト（W01_Tester_CheckList.md）の選定理由およびテスト設計の方針をまとめたものです。

## 1. テスト設計方針

基本仕様書に基づき、**ブラックボックステスト**の観点から、システムの機能要件・非機能要件（セキュリティ等）を網羅するように設計しました。以下の観点を重視しています。

1. **正常系（Positive Testing）**: ユーザーが正しい操作を行った場合に、システムが仕様通りに動作するか。
2. **準正常系・異常系（Negative Testing）**: 誤った入力や許可されていない操作を行った場合に、適切にエラーハンドリングされるか。
3. **境界値分析（Boundary Value Analysis）**: 判定の境界となる値（在庫0、最大貸出冊数5冊など）での挙動確認。
4. **権限確認（Role-based Access Control）**: 一般ユーザーと管理者でアクセス権限が正しく分離されているか。

## 2. 各テスト項目の選定理由詳細

### 2.1. ログイン・認証 (TC-01 ~ TC-06)

- **選定理由:** システム利用の入り口であり、セキュリティの基本であるため。
- **重点項目:**
  - ユーザーと管理者のログイン可否（TC-01, TC-02）。
  - 必須入力項目のバリデーション漏れがないか（TC-03, TC-04）。
  - 認証エラー時のメッセージが仕様（具体的すぎず適切か）通りか（TC-05）。
  - **セキュリティ:** ログインバイパス（URL直接入力）が防がれているか（TC-06）。

### 2.2. 書籍検索 (TC-07 ~ TC-09)

- **選定理由:** ユーザーが最も頻繁に使用する機能であるため。
- **重点項目:**
  - **論理削除の確認:** 削除された本が「物理的に存在していても検索結果に出ない」という仕様（TC-09）はバグが起きやすいため最重要確認項目としました。
  - 曖昧検索の利便性確認（TC-08）。

### 2.3. 貸出機能 (TC-10 ~ TC-15)

- **選定理由:** ビジネスロジックの中核であり、複雑な条件（在庫、冊数制限、日付計算）が含まれるため。
- **重点項目:**
  - **境界値テスト:** 特に「貸出上限5冊」の仕様に対し、5冊借りられること（TC-12）と、6冊目が拒否されること（TC-13）の境界を確認します。
  - **在庫管理:** 0冊の場合の挙動（TC-11）。
  - **日付ロジック:** 「土日延長ルール」はシステム日付に依存する複雑なロジックであるため、特定の曜日を狙ったテストケース（TC-15）が必須です。

### 2.4. 返却機能 (TC-16 ~ TC-17)

- **選定理由:** 在庫整合性を保つために重要。
- **重点項目:**
  - **二重返却の防止:** 連打やブラウザバックによる不正な在庫増加（TC-17）を防げるか確認します。

### 2.5. 管理者機能・データ整合性 (TC-18 ~ TC-23)

- **選定理由:** データの破壊や不整合を防ぐため。
- **重点項目:**
  - **参照整合性:** 「貸出中の本は削除できない」（TC-21）は、これを満たさないと貸出データが宙に浮く（迷子レコードになる）重大な不具合につながるためテスト必須です。
  - **権限分離:** 一般ユーザーが管理者機能をURL直打ちで実行できてしまう脆弱性（IDOR/権限昇格）がないかを確認します（TC-23）。

## 3. 今後の拡充案（Scope Consideration）

今回のリストは基本仕様書に記載された範囲のみを対象としていますが、実務的には以下のような観点も必要になる可能性があります。

- **セッションタイムアウト:** 長時間放置後の操作。
- **排他制御:** 同時に最後の1冊を複数のユーザーが借りようとした場合。
- **XSS/インジェクション:** 入力フォームへのスクリプト埋め込みテスト。
